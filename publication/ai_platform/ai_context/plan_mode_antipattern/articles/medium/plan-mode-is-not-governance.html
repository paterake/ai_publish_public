Plan Mode Isn't Governance (And Governance Is What Scales)

Image created by the author using Midjourney

Every article and video I found on AI coding assistants said the same thing: plan first, then build. Use plan mode, review the approach, then let the assistant implement.

I tried it. The plan was useful — until I hit a rate limit, ran out of context, or needed to switch to a different agent. At that point I'd copy the plan mode output into a new session, rebuild context, and pick up where I left off.

I did this enough times that it stopped feeling like a workflow and started feeling like the problem.

What I do instead

Plan mode was generating the plan in the right place for one session. It was never designed to survive the session ending.

So I stopped using it. Instead I forced the agent to externalise everything: a PRD built from my intent, a backlog catalog the agent could read cold in any session, a checkpoint written back before closing. The next session opens, reads the backlog, picks up exactly where the last one left off.

I've worked through multi-day refactors this way — swapping between Claude Code, Trae, and Qwen Code as rate limits hit, across sessions that stretched over days. The work stayed consistent. Not because I had a good plan at the start, but because the plan was always in the files.

Why plan mode makes complex work harder

Plan mode solves one thing: it stops the assistant from writing code before you've agreed on an approach. Reasonable guard inside a simple workflow — ask for a change, approve the plan, let it implement.

For anything more complex, that workflow breaks down before plan mode even comes into play.

I've had implementations that required rework across multiple modules — not because the approach was wrong, but because one design decision had cross-cutting implications that only surfaced mid-build. A planning conversation at the start of a session wouldn't have caught that. What it would have done is consume context: the plan sits in the same window as the implementation, and as the session grows, quality erodes. Not because the plan was wrong — because there isn't enough room left to execute it well.

Plan mode is session-scoped. It scales to session-sized problems.

What makes the workflow hold

The contract layer comes first. A small set of documents defines how work must be done: the non-negotiable constraints, the conventions that prevent drift, the triggers that govern what gets updated when. Not documentation for humans — the steering mechanism that keeps any assistant convergent, regardless of which session or which tool.

PRDs hold when they capture intent rather than approach. They rot when they describe implementation strategy — or at least they do once the implementation starts moving. A future session reads the stale "how", reintroduces it, and you get inconsistency across modules. What holds is capturing why the module exists, what constraints must hold, what "done" means. In practice: I define intent, the agent builds the PRD and the backlog from it.

Sessions are scoped to bounded work, not long runs. A series of short sessions, each covering one backlog item, each writing a checkpoint before closing — accumulated constraints forwarded explicitly. The session ends; the knowledge doesn't.

The thing that changed how I think about this

I had a gate catch a drift I would have reviewed as a clean diff. A check that ran automatically, failed fast, and surfaced something I'd have missed in review.

That's when the governance layer stopped feeling like overhead and started feeling like enforcement. A rule without a failure signal is just a preference. Encode it as something that fails fast, and it holds regardless of context length or which assistant you're using.

The practical test

Close every session. Start a new one with a different assistant, point it at the repo contracts. Consistent work across that boundary means you have governance. Anything less and you're relying on session memory.

Plan mode works for small, self-contained asks — a single session, no cross-module implications. In practice it has never come up for anything more complex than that. For cross-cutting work it makes things worse: the planning conversation consumes context the implementation needs, and quality degrades before you're halfway done.

The point

Planning is a principle: understand before changing. Plan mode is one implementation surface — a chat-state gate. If you want the principle to scale, it needs a surface that outlives the session.

The plan should already be in the files.
