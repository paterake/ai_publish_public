The LLM that builds your system is not the LLM that runs inside it

Image created by the author using Midjourney

When cloud coding assistants (Claude Code / Trae / Qwen Code) can’t touch your data, LLMOps gives them the evidence trail to iterate on a local LLM system without seeing the data.

I use LLMs (generative AI) in two places at once.

One LLM helps me build the system. It reads requirements, proposes code changes, and refactors modules.

Another LLM runs inside the system. It classifies, retrieves, scores, and decides whether the evidence is good enough to proceed.

In my case, those roles are split deliberately. The build loop uses cloud coding assistants, while the run loop uses local LLMs via Ollama (for example qwen2.5:7b, qwen3.5:9b, plus a local embedder like nomic-embed-text). The workload processes real operational data, and the constraint is "data stays inside the system", so the cloud assistants can’t execute the pipeline against that data.

The cloud models don’t even see the raw inputs or the raw outputs. They only see the LLMOps evidence: run IDs, manifests, summaries, and telemetry. That lets the builder make calibrated decisions from deterministic signals (typed errors, budgets, validation gates, cache behaviour, latency, token/cost estimates) without pushing sensitive data to the cloud just to establish correctness.

This wasn’t an "aha" moment or a reaction to a problem. It was a deliberate architecture: build in the cloud, run locally, and connect the two with an evidence trail that the build-side assistants can read. The system didn’t become production-ready by luck or by a single prompt. It became production-ready because the assistants could route from local run results back into code or config, then re-run until the outputs were bounded, validated, and repeatable.

This article is about what happens when you connect those two loops. It’s about AI building a system that itself depends on an LLM, then iterating against real runs:

  • run the pipeline against a local model
  • review a run summary and correlated telemetry via a run ID
  • adjust code or runtime parameters (temperature, top‑p, top‑k, whether the model’s "thinking mode" is enabled)
  • tune caching and rerun

In many projects those two things get blurred into one phrase: "we’re using AI".

That blur creates a role mix-up.

The controls you need for a coding assistant are not the controls you need for a pipeline model. The roles fail in different ways. If you apply development-style assumptions to the pipeline role (or production-style approval overhead to the developer role), you get predictable failure modes:

  • You add approval gates and change tickets to development and still miss real production risks.
  • Or you accept "assistant-style" looseness in a pipeline and ship silent wrong answers.

In my setup, cloud coding assistants build and review, while local models run via Ollama. That split is driven by data constraints. The controls that matter are the ones that let the builder review local execution safely: run artefacts, bounded runs, and correlated telemetry.

By "LLMOps" I mean the execution trace contract the system emits on every run so the builder can review what happened without moving the data or replaying the run. In practice it’s a small set of artefacts that fit together:

  • a run ID (run_id) that correlates artefacts for a single execution
  • a per-run manifest (status, timings, fingerprints, typed errors, degrade mode)
  • structured telemetry keyed by run_id (latency, token/cost estimates, cache hits, error types, trace IDs)
  • a derived run review that rolls up warnings and points you at the exact artefacts to inspect

In this article, "assistant" means the LLM plus its harness (tools, rules, and deterministic gates). I avoid "agent" here because, elsewhere, "agent" often implies an autonomous tool-loop running inside the system.

A simple distinction that changes everything

Most teams treat "using AI" as a technology choice. In practice it’s a loop design choice: who runs what, where the data is allowed to go, and how you review execution.

I treat them as two different roles.

Developer AI writes and changes the system. The loop is interactive: it proposes; I accept or reject; tests and hooks do the enforcing. When it’s wrong, it’s wrong in public.

Worker AI runs inside the system. The loop is unattended: retries, timeouts, and "looks fine" outputs can slip through unless you box it in with budgets, observability, degrade modes, and validation at the boundary.

The trap is that because both are "LLMs", the natural instinct is to treat them as needing the same constraints.

They don’t.

The developer AI: optimise for controllability

A coding assistant is allowed to be wrong in a way production systems are not.

The control loop is different:

  • A developer AI proposes.
  • A human reviews and accepts or rejects.
  • The codebase’s tests and hooks enforce deterministic guardrails.

The safety property doesn’t come from the assistant "being careful". It comes from the fact that the assistant cannot ship anything without passing through multiple deterministic gates.

Here’s a concrete example of a gate that matters more than any prompt:

  • If a command looks like a push to the default branch, the session defers and requires human approval.

The assistant has no choice about it. The gate makes a high-risk action structurally harder than a safe one.

Most AI safety writing focuses on model behaviour — prompts, alignment, making the model more careful. But that gate doesn't ask the model to be careful. It just blocks the action. That's the thing that changed how I build: less about whether the assistant will make good decisions, more about whether the system lets dangerous ones through.

The worker AI: optimise for bounded execution

When a model runs inside a pipeline, the primary engineering concern is not that it produces a low-quality paragraph.

The primary concern is that it behaves like an unbounded subsystem: it retries without stopping, times out without signalling, returns empty answers that look like legitimate "not found" results, and burns budget without producing evidence.

The defining difference is unattended execution. The worker AI runs when nobody is watching.

That changes the non-negotiables:

  • Every call must have a time budget.
  • Runs need a correlation ID.
  • Every failure must degrade predictably.
  • Outputs need validation against a defined contract.

This is not "LLM safety" as ethics. It’s LLM safety as systems engineering.

I've debugged distributed jobs that "completed successfully" but produced nonsense. The most expensive failure mode is the one that looks like success.

In a pipeline, a confident wrong answer is more damaging than an explicit error.

So the control posture flips:

  • Developer AI is allowed to be creative because it is constrained by review.
  • Worker AI must be boring because it is constrained only by the system you build around it.

The non-obvious case: one system, two feedback loops

It’s tempting to treat "model choice" as the core decision. But in this setup the builder and the runner are intentionally different models: one lives in the IDE and is human-adjudicated, the other lives inside a pipeline and runs unattended.

The decision is: what role is the model playing right now, and what controls apply to that role?

This is why I treat these as three layers:

  1. Model (the underlying capability)
  2. Harness (skills, rules, hooks, session constraints for developer AI)
  3. LLMOps (budgets, observability, degrade modes, validation for worker AI)

It’s common to invest heavily in layer 2 and assume layer 3 is solved as a by-product.

It isn’t.

They solve different problems.

When AI builds AI: the control loop becomes the product

The developer assistants built the solution, then wired in execution controls via a shared ops layer: run IDs, bounded budgets/timeouts, correlated telemetry, and caching controls. That matters because the next step wasn’t "ship the code". The next step was to run the system against a local model (for example qwen2.5:7b or qwen3.5:9b via Ollama) and see what happened.

This showed up across multiple modules: once they all share the same ops layer, the assistant can iterate in a disciplined way instead of debugging each module as a one-off.

Once the controls were in place, the loop looked like this:

  • Run the pipeline and capture a run ID.
  • Review telemetry correlated to that run (timeouts, retries, evidence gates, cache hits).
  • Adjust the code, or adjust the runtime model parameters (e.g. temperature, top‑p, top‑k, whether the model’s "thinking mode" is enabled).
  • Tune caching and summarisation so the system spends tokens where it matters.
  • Re-run.

A human could do this loop once or twice. But across multiple modules, with each rerun producing a new set of telemetry, the volume of structured evidence quickly exceeds what a human can usefully process. I would have become the bottleneck, not the asset — slowing the loop down and adding little value at the point where the AI is fastest. My judgment mattered at two points: defining what "good" looks like before the first run, and deciding whether the final result was acceptable. Everything in between was faster and more consistent with the assistant in the loop.

Those parameter adjustments are literal config edits, not prompt rewrites, not code changes. Here is a representative slice of what the cloud assistant can change between runs without touching the underlying data:

llm:
  model: qwen3.5:9b
  temperature: 0.1        # low: reduces variance; outputs stay reproducible across runs
  max_tokens: 3000
  timeout_seconds: 240
  thinking: false         # off: burned the generation budget and returned empty responses

max_retries: 1
max_parse_retries: 2
backoff_mode: exponential
max_backoff_seconds: 30.0

Temperature, token limits, timeout, thinking mode, retry caps, backoff strategy. All in config. The cloud assistant reviews a run summary, identifies the failure class, and edits the values. No data crosses the boundary.

What made the loop workable was mundane.

First, everything is keyed off the run ID. That turns "the model behaved oddly" into "this specific run behaved oddly", which means the assistant can reason from concrete evidence rather than vibes.

Second, the system summarises run results before it deep-dives. The assistant can start with a compact run summary (token economy) and only pull low-level telemetry when the summary suggests a real problem. That is a control choice too: summarisation is not a convenience feature, it controls what the assistant looks at and what it spends.

This only works because the system writes down what happened. Not as vibes or a narrative, but as deterministic artefacts. Every run writes a manifest keyed by run_id (status, error counts, model identifier, fingerprints for config/inputs, and file hashes for primary artefacts). A separate run review then aggregates those artefacts and points you to the relevant telemetry and outputs.

Here is the shape of the summary that makes the loop practical (redacted, but real enough to be testable):

run_id: … (uuid)
model: … (local)
params: thinking=…, temperature=…, top_p=…, top_k=…

status: ok | degraded
quality_gates: passed=… failed=…
fallback_loops: triggered=… max_iterations_hit=…

llm_calls: …
timeouts: …
parse_repairs: …

caches: hit_rate=… writes=…
token_estimates: prompt≈… output≈…

Even when you don’t keep "pretty" before/after examples around, the system still produces hard evidence during test runs. A run review is a small JSON summary that points at the exact artefacts the assistant can inspect.

Example run review excerpt (redacted):

{
  "run_id": "…",
  "status": "ok",
  "verdict": "ok_with_warnings",
  "warnings": ["error_counts.context_overflow=1"],
  "artifacts": {
    "run_manifest": "…/run_manifest.json",
    "telemetry_jsonl": "…/events.jsonl",
    "run_log": "…/run.log"
  }
}

And the corresponding manifest excerpt that makes the warning actionable:

{
  "run_id": "…",
  "status": "ok",
  "error_counts": { "context_overflow": 1 },
  "degrade_mode": "refusal_with_suggestions",
  "config_fingerprint": "…",
  "inputs_fingerprint": "…"
}

That’s enough for the assistant to diagnose the class of failure ("prompt too large"), then decide whether the next change belongs in code (tighter chunking/limits), in configuration (smaller context budgets), or in prompting (more aggressive summarisation), without a human stepping through raw logs.

A few concrete examples are what made this credible in my own work.

First, in the visualisation pipeline, enabling the model’s "thinking mode" looked like it should improve reasoning. In practice, on Qwen3.5:9b it could burn the generation budget and return an empty response, which then cascaded into missing or malformed chart output. The fix was not moralising about prompts. The fix was a control: default thinking to off for publication runs, keep temperature low, and treat parse repair as a bounded retry rather than an open-ended loop.

Second, we hardened visual outputs by treating prose as untrusted at the boundary. The charts and metrics stay deterministic. If the model writes narrative over them, it is only allowed to use numbers that appear in the telemetry-derived facts payload; any unsupported number triggers deterministic fallback phrasing. That is the difference between "the model usually behaves" and "the system cannot publish a wrong number".

Third, in the classifier, we stopped treating the LLM as the first step. We added a five-layer reuse waterfall (cheap similarity layers before expensive inference) so cost scales with novelty, not dataset size. Most queries never touch the model at all. The cheap layers operate in milliseconds; an LLM call is orders of magnitude slower. Under heavy local load, we also needed a circuit-breaker style fallback so embedding calls don’t repeatedly stall the entire run when resources are saturated.

Fourth, in retrieval, the system does not accept "non-empty" as success. A fast path produces a draft record, then a deterministic quality gate decides whether it is safe to accept. Only failures escalate into a bounded recovery loop, and that loop has hard caps so it cannot grow into an unbounded subsystem.

Across all four, the boundary between roles is operational, not philosophical. The human defines intent and hard targets up front (taxonomy, validation contracts, known-good reference datasets and renderers). After that, the system can self-check: the classifier’s outputs can be re-rendered and compared, and the visualisation pipeline can be judged against deterministic expectations without needing a human to "eyeball" every run.

This is the net effect: cloud coding assistants iterate on a system that executes locally on different LLMs, using bounded runs and correlated telemetry to converge. The result is an evidence-driven AI↔AI loop: build → run → review → tune → re-run.

The mix-up in the wild

1) Applying production approval processes to the developer loop

Teams require detailed telemetry, change tickets, or heavyweight approval processes for every assistant-generated diff.

The result is predictable:

  • the assistant becomes too slow to use
  • engineers bypass the process
  • the "controls" become theatre

The right controls for developer AI are not bureaucratic ones. It’s fast deterministic gates: formatters, linters, tests, and "no-go" hooks for dangerous actions.

2) Bringing assistant permissiveness into production

Teams allow a pipeline LLM to "just try again" or "produce something useful" when evidence is missing.

That feels helpful in an interactive assistant. In production it’s a risk.

If the system cannot find evidence, it must say so explicitly and degrade cleanly. Otherwise you are training your downstream consumers to trust outputs that were generated in the absence of supporting facts.

3) Using the same quality standard in both roles

In development, quality is evaluated by the human in the loop: you read the output, decide if it's good enough, and move on. That works because the feedback loop is immediate and you are present for every output.

In production, the system runs without a reviewer. Avoid treating "it looked right when I tested it" as a quality standard; quality has to be measured by the system, on every run.

The failure mode is delayed discovery. You find out the output was wrong when something fails three steps later, or three days later.

The production quality model is different by necessity. You cannot eyeball it. Quality must be measured by the system, against a defined standard, on every run. If the worker AI cannot produce evidence that meets a gate, it must degrade explicitly rather than continue. A plausible-looking wrong answer that bypassed no quality check is the most expensive failure mode in production AI. It is confident. It is invisible. It has a long runway before it surfaces.

A simple way to tell the difference

Ask: when this output is wrong, who finds out first?

If it’s you, in the same session, you can fix it immediately. Speed matters more than perfection. That’s the developer loop.

If it’s a downstream user, a customer, or a dashboard three days later, that’s the expensive kind of wrong. By then the output has already acted, been trusted, or propagated. That’s the production loop, and it’s the one you have to design against.

Key takeaways

  • Cloud coding assistants (Claude Code / Trae / Qwen Code) can iterate on a local-only system by reviewing run artefacts: run IDs, summaries, manifests, and telemetry.
  • "AI builds AI" is an outer loop: the coding assistants change code around an inner LLM whose behaviour is visible only through execution evidence.
  • The practical pattern is summaries first (token economy), deep telemetry only when the summary flags a problem.
  • Controls still matter, but they are in service of iteration: bounded runs, explicit degrade modes, and validation at the output boundary.

This project's articles fall into two chapters: one on how the developer loop is constrained (harness, memory, plan mode), and one on how the worker loop is constrained (ingest, retrieval, classification). They are different control regimes applied to the same system. This is the article that connects them.

I’ve stopped asking "are you using AI?"

The useful question is which role the model is playing right now, and what controls apply to that role.

Treating controls as role-based is how you avoid both extremes: development slowed by approval overhead, and production destabilised by assistant-style looseness.

This framing may evolve as the tooling matures, but the basic split has held up well in my own work.
