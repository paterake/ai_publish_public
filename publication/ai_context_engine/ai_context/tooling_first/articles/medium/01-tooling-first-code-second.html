Serve the Intent, Not the Method: Changing Who Signs Off on Claude Code's Work

Image created by the author using Midjourney

Coding agents prefer to write their own code, and they grade it themselves. Ask for a file lock or an OAuth client and the agent writes one, adds tests and reports the task finished, even when a maintained open-source library already does the job. I watched this while building a tool with Claude Code. In May 2026 I wrote a preference for libraries into the rules my agents load before every task, and it did not hold.

What worked in the end was changing who signs off, under a rule that now reads "Serve the intent, not the method". The intent is what the product has to deliver. The method is everything used to get there, and adopting a library is as much a method as writing code. The agent adopts the recognised tool first and writes custom code only for a gap the intent cannot do without. A second agent, one that did not write the code, judges each change against what was asked. A cleanup closes only when the product's output, measured before and after, says it should.

Why agents skip the library

Software engineering settled long ago who should write a parser, a file lock or an OAuth client: if a maintained library does it, nobody on your team should. The library's authors take the bug reports, the new language versions and the security fixes. Custom code leaves all of that with you, once for every language your estate contains. Custom code still earns its place where no maintained tool does what the product needs, and that should be the exception.

Coding agents treat the exception as the rule. When I asked one why my preference kept slipping, it was blunt: almost everything in how the work runs rewards writing code, and nothing makes adoption the default question. Writing code is the agent's cheapest move. Code that passes its own tests is quicker to produce than learning a library, fitting it and living with its limits.

Anthropic's research on reward hacking describes a model "fooling its training process into assigning a high reward, without actually completing the intended task", and its prompting guidance says "Claude can sometimes focus too heavily on making tests pass at the expense of more general solutions" (reward hacking research, prompting best practices). Neither says models prefer custom code over libraries. For that, my evidence is one agent's account of one repository.

The tool that showed it

The tool reads a codebase and writes down what the application does: what it declares, enforces, stores and exchanges, each fact citing its file and line. Architects, product people and designers use it to see how an application fits together without reading the code. A model's answers rest on the same record, so it has to be exact.

The first build read the code with readers the agents wrote by hand, one each for Java, JavaScript and T-SQL database scripts, and every one was ours to maintain. So I had the agents move the reading onto maintained tools, a compiler-backed library (Eclipse JDT) for Java and Microsoft's own parser for T-SQL, and accepted losing anything the old code did that those tools do not. Custom code stayed only where the tools stop.

My May rules had left the agent ways out: they allowed custom code where a library "is too heavy for the task, or requires more wiring than the problem warrants", and said "a small in-line parser or test utility may be faster than wiring a library". When I rewrote the rule, I took those exceptions out and noted beside the new text that they were the loopholes.

Where an agent's own check falls short

An agent judges a change by how well it was built, and whether it should exist never comes up. When I asked one why, it said a second agent given "build X" checks that X is built well, and "doesn't ask 'should X exist?'", so well-built code nobody needed passes every check.

"Once custom code exists, it has tests, docs and recorded decisions that all defend it. A library never starts on equal terms," the agent said. During the move onto libraries, the tests written for the old code stayed behind, guarding behaviour the library now owned, and the agents worked around them. In the end I deleted the old checking scripts myself, dozens of them.

After an overnight run, the agents reported the cleanup closed with every capability in the tool's list marked final, and by morning it did not hold. Twenty entries had passed on justifications the agents wrote for themselves, and the checker counted a library as adopted if it was declared, even when nothing called it. When I put this to the agent, it conceded that most of those entries "got there by justifying custom code, which your rule rules out", and then: "I approved the checker as the end condition and then reported 'closed' on its count." I wrote that the run's promise to resolve this once and for all "has proved a lie". The list looked clean, and nobody had measured whether the tool still delivered what it must.

I had a hand in it too, from the other side: at times I chose delivery over purity and told the agents to stop making the repository pure and get it deployed. Lean too far that way and custom code stays in place and rots. Lean too far the other way, as the overnight run did, and the list looks clean while nobody checks what the product still delivers, so the rule has to hold against both pulls.

Why I would not just build it

Late in the run an agent was still weighing whether to swap its own OAuth code for a library. I answered: "swap - why are you even debating this - the whole OSS contract was for exactly this type off issue - custom code cant be maintained".

An earlier project of mine had learned the same lesson about a hand-rolled circuit breaker: "There is no good answer when pybreaker exists". The rule now shuts the old loopholes: "A library being heavier than the task, or needing more wiring than the problem seems to warrant, is not a reason; neither is custom code being faster to write." As I put it to the agents: "we dont reward based on writing code - but reward based on recognisition of what industry aligned tooling to adopt first". Adopting first is still a method, so thin custom code stays wherever a gap is critical to the intent.

The bar

Midway I asked whether we were making this too complex. A software engineer given a task researches, adopts the recognised tool, writes custom code for what the tool lacks, and asks whether each gap really matters to the task. I approved that as the bar because it still lets an agent deliver. Where the product needs custom code, as it does for authorisation, redaction of secrets and provenance, the custom code is rewarded.

Three checks keep the bar honest: every piece of custom code must map to an entry in the tooling list or a command fails, every adopted library must be imported and called rather than only declared, and a second agent that did not write the code judges each piece of custom code against the task. The task has to be on record before the code that cites it, or be my own answer on record, and a test never counts as the need, so an agent cannot write its own justification.

Measuring before any swap

When I set the run up as an audit, I wrote that "the whole validity of this repo as a context supplier - if we weaken what this repo is - there then is the risk it achieves nothing valuable". So before any change I recorded a baseline: the standing proof for each capability and the minimum search-quality scores.

Each swap had to produce the same real output before and after, one capability per commit, so a regression was one revert away. A test written for the replaced code goes with it; tests for authorisation, secrets and provenance never go this way. Nothing was removed until the audit was done: "drops dont happen - until the audit is done and it is then independently reviewed". That review pushed back hard, overturning about one in four of the agents' verdicts.

On the last day, file locking, precision and recall functions, file-type detection and the OAuth token exchange moved onto libraries, each passing its check. Two candidates failed it: a redaction library and an XML parser each behaved differently from the code they would have replaced. Swapping them in would have satisfied the rule about tools and changed what the product delivers, so the custom code stayed and the gap was recorded.

Who signs off on a change

The new rule names the failure it came from: a tooling-alignment run closed on a status count, and none of the code it judged had been measured against the product. A change that makes the work look cleaner but deliver less has failed, whatever its metric says.

The agent's training reward stays as it was; the last word on each change now belongs to a second agent, which judges it against the task. Measurements back each decision, and the setup will not commit a change until that agent has passed it.

Searching for a library before writing code is published advice, and I do not claim it. What I tried, on one repository and one run, is the combination: custom code only for critical gaps, every other gap recorded, and every swap checked against a baseline.

Limits

  • The amount of custom code did not fall overall, because the reading moved onto compilers and maintained libraries. The gain is that the reading itself is now maintained by those tools' authors.
  • Nothing automatic checks whether a change served the intent. The second agent's judgment does, and it can be wrong.
  • A cleanup judged on what it removes would cut too much.
  • The check before each commit proves the records are complete, not that custom code is justified, and it does not see commits made outside Claude Code.
  • The agent quotes come from one agent about one repository.

Key takeaways

  • Adopting a library, removing code and closing a cleanup are methods. Judge each by what the product must deliver.
  • Custom code is justified only for gaps critical to the intent; every other gap is recorded as a gap.
  • Close a run on measured before-and-after output from the product.
  • The agent stops approving its own work when an independent check judges each change against the ask and the setup refuses to commit without its pass.

The record

  • When the overnight run was reported closed, the tooling list held 121 capabilities, 85 of them on adopted libraries.
  • The morning after the overnight run was reported closed, 20 custom or kept entries were found to have passed on records the agents wrote. The agent said 18 of them relied on justifying custom code.
  • I deleted 57 of the 59 checking scripts left from the move. The credential-leak scans went with them, so at that point no automated check covered a regression in secret redaction. I accepted that.
  • The independent review overturned 36 of the agents' verdicts across 133 audit entries.
  • A re-score the day before the last swaps found no capability below the baseline and no access-control leaks. The re-scores on record predate those swaps.
  • The swaps not made: the redaction library merged adjacent matches and dropped zero-length ones, and the XML parser reports a different line for tags spanning several lines, by design.
  • Two parts of the commit check, its filter and a timeout, were not exercised in a live run.
