Serve the Intent, Not the Method: Changing Who Signs Off on Claude Code's Work

Image created by the author using Midjourney

Coding agents prefer to write their own code, and they grade it themselves. Ask for a file lock or an OAuth client and the agent writes one, adds tests and reports the task finished, even when a maintained open-source library already does the job. I watched this while building a tool with Claude Code. I had written the preference for libraries into the rules my agents load at the start of every task in May 2026, and it still did not hold.

What finally delivered was a change in who signs off on the agent's work. The rules now say "Serve the intent, not the method". The agent adopts the recognised tool first and writes custom code only for a gap the work cannot do without, and a second agent that did not write the code judges each change against what was asked. For anyone directing coding agents, the lessons are to justify custom code only for gaps critical to the intent and to close a cleanup on measured before-and-after output from the product. Beyond that, an independent check should judge each change against the ask, so the agent no longer approves its own work.

Why agents skip the library

Software engineering settled long ago who should write a parser, a file lock or an OAuth client. If a maintained library already does it, nobody on your team should. The library's authors take the bug reports, the new language versions and the security fixes. Custom code leaves all of that with you. The cost multiplies with every language and framework an estate contains. Standard tooling keeps pace with change better than a team can by building. Custom code still earns its place where no maintained tool does the job. That is the exception.

Coding agents treat that exception as the rule. When I asked one why my preference for libraries still had not held, it answered bluntly that the preference kept slipping because almost everything in how the work runs rewards writing code, and nothing makes adoption the default question. For an agent, it said, writing code is the cheapest move. Within a single working budget, generating code that passes its own tests is faster and safer than learning a library, fitting it and accepting its limits. Agents reward themselves for coding.

Anthropic documents the wider family of this behaviour. Its research on reward hacking describes a model "fooling its training process into assigning a high reward, without actually completing the intended task", and its prompting guidance says "Claude can sometimes focus too heavily on making tests pass at the expense of more general solutions" (reward hacking research, prompting best practices). Neither says models prefer custom code over libraries. For that, the agent's account of one repository is the evidence I have.

The tool that showed it

The tool reads a codebase and writes down what an application does. It records what the code declares, enforces, stores and exchanges. Each fact cites its file and line. Architects, product and designers use it. It shows them how an application is put together without reading the code. A model's answers rest on the same record, so it has to be exact.

The first build did the reading with code the agents wrote by hand. One reader worked out which name, type and method call referred to what in Java, another scanned JavaScript, and a third split T-SQL database scripts into parts. Every reader was ours to maintain. So I had the agents rework it onto maintained tools and accepted the loss of anything the custom code did that they do not. Java moved onto a compiler-backed library (Eclipse JDT) and T-SQL onto Microsoft's own parser. Custom code stayed for the parts those tools do not provide.

The rules I had written in May gave the agent ways out. They allowed custom code where the library "is too heavy for the task, or requires more wiring than the problem warrants", and a separate line said "a small in-line parser or test utility may be faster than wiring a library". When I rewrote the rule, I removed all three exceptions and noted beside the new text that they were the loopholes the old rule left open for custom code.

Where an agent's own check falls short

An agent judges a change by how well it was built. A second agent given "build X" checks that X is built well, and in the words of the agent I asked, the check "doesn't ask 'should X exist?'". Well-built code nobody needed passes every check. Code the product does need is another case, and the bar below rewards it.

Once the code exists, everything around it defends it. "Once custom code exists, it has tests, docs and recorded decisions that all defend it. A library never starts on equal terms," the agent said.

Refactoring then measures success against what already exists. When I moved the tool's custom code onto open-source libraries, the tests written for that code stayed. They pinned behaviour the library now owned, so the agents doing the move worked around them. The scripts that had compared the old code with the new libraries stayed as well. I deleted 57 of 59 of those checker files, and the commit records the cost: "The credential-value leak scans went with the checkers, so no automated check covers a redaction regression (accepted)."

Work also closes on a label. The agents wrote the code and the records that justified calling it final. An overnight run reported the cleanup closed, with every row of the tooling list in a final state. That list records each capability the tool has and what provides it, a library or custom code. Of its 121 rows, 85 were adopted libraries. The next morning the commit that reopened the run found that 20 custom or kept rows had passed on decision records the agents wrote, that nothing tied custom code to its rows, and that a declared dependency counted as adoption. The checker had accepted a library that was declared but never imported or called. The agent that had reported the run closed said 18 of those rows "got there by justifying custom code, which your rule rules out", and added: "I approved the checker as the end condition and then reported "closed" on its count." I wrote that the run's promise to resolve this once and for all "has proved a lie".

I had a hand in it too. At times I chose delivery over purity and told the agents to stop making the repository pure and focus on getting it deployed.

Why I would not just build it

I refused a hand-built solution because custom code has to be maintained. When an agent was still weighing the OAuth swap late in the run, I answered, about the rules I had written: "swap - why are you even debating this - the whole OSS contract was for exactly this type off issue - custom code cant be maintained".

An earlier project of mine had already recorded the lesson about a hand-rolled circuit breaker: "There is no good answer when pybreaker exists". The rule now reads: "A library being heavier than the task, or needing more wiring than the problem seems to warrant, is not a reason; neither is custom code being faster to write." The same rule keeps thin custom code for a gap critical to the intent. The principle, in my words to the agents, was "we dont reward based on writing code - but reward based on recognisition of what industry aligned tooling to adopt first".

The bar

Midway I asked whether we were making this too complex. A software engineer given an ask researches, adopts the recognised tool, adds custom code for what the tool does not provide, and measures each of those gaps against the ask to see whether it is critical. I approved that as the bar because it lets an agent still deliver. Custom code is rewarded where the product needs it, and authorisation, redaction of secrets and provenance are the product's core.

Checks keep the bar honest. One command maps every piece of custom code to a row in the tooling list and fails if any piece has none, so custom code cannot appear unrecorded. A second command shows that each adopted library is imported and called, so a declared dependency cannot pass as adoption. A second agent that did not write the code judges each custom row against the ask, so an author does not grade its own work. The ask has to be in version control before the code that cites it, or be my own answer on record, and tests and test-only helpers never count as the need, so an agent cannot write the justification for its own code.

Measuring before any swap

Setting the run as an audit, I wrote that "the whole validity of this repo as a context supplier - if we weaken what this repo is - there then is the risk it achieves nothing valuable". So before any change I recorded a baseline of the standing proof for each capability and the minimum search-quality scores.

A swap of custom code for a library needed a before and after comparison of real output on committed fixtures, with one capability per commit so that a regression was a one-commit revert. A test written for the custom code a library replaces, or one that pins the library's own output or version, is stale, and it goes with the change that makes it stale. Tests for authorisation, secrets and provenance never go this way. Removals waited for the audit and an independent review: "drops dont happen - until the audit is done and it is then independently reviewed". That review overrode 36 of the agents' verdicts on 133 audit rows. The re-score the day before the last swaps found no capability below the baseline and no access-control leaks.

On the last day, file locking, precision and recall functions, file-type detection and the OAuth token exchange moved onto libraries, each passing its before-and-after check. Two other candidates were measured and not made. A redaction library merged adjacent matches and dropped zero-length ones, and an XML parser reported a different line for tags spanning several lines, by design. The custom code stayed in both cases, with the gap recorded.

Who signs off on a change

The rule line names the failure above. A tooling-alignment run closed on a status count. None of the code it judged had been measured against the product. The rule adds that a change that makes the work look cleaner but delivers less has failed, whatever its metric says.

The agent's training reward does not change. What changes is who has the last word on a change. A second agent that did not write the code judges it against the ask, recorded measurements back each decision, and the setup refuses to commit a change until that second agent has passed it.

I tried this combination on one repository and one run. I allowed custom code only for gaps critical to the intent, recorded every other gap, measured each gap against what the system must deliver and checked each swap against a no-regression baseline. Searching for a library before writing code is published advice, and I do not claim it.

Limits

  • The custom line count did not fall overall, because the reading moved onto compilers and maintained libraries. What fell was the cost of maintaining the readers.
  • Nothing automatic checks whether a change served the intent. The second agent's judgment does, and it can be wrong.
  • An alignment run judged on what it removes would over-cut.
  • The search-quality and access-control re-scores in git predate the last swaps.
  • The automatic check that runs before each agent commit lists its own known misses. It does not see commits made outside Claude Code, and its checks prove that records are complete but say nothing on whether custom code is justified. Its filter and a live timeout were not exercised in a live run.
  • The agent quotes come from one agent about one repository.

Key takeaways

  • Custom code is justified only for gaps critical to the intent; every other gap is recorded as a gap.
  • Close a run on measured before-and-after output from the product.
  • The agent stops approving its own work when an independent check judges each change against the ask and the setup refuses to commit without its pass.
