14 LLMOps Primitives, Zero Cloud Dependencies

Image created by the author using Midjourney

These primitives were not designed. Every failure that had no signal forced the agent to build one. Eventually, those signals caught failures in the primitives themselves, and the agent replaced them.

A coding agent working at pace generates more code than one reviewer can check for correctness. A pipeline processing ten years of operational data in a single run makes thousands of model calls, more than any human can inspect for correctness. The data stays on-machine too, the coding agent cannot read source inputs or model outputs to diagnose failures. The signals are the review mechanism. Every primitive in this article was built to make one class of failure visible that previously had none: the reconciliation check caught ingestion fragmentation that raised no error; the retrieval quality checker caught retrieval regression visible only in degraded answers; the circuit breaker caught provider stalls before they consumed the run budget silently.

Those signals eventually caught failures in the agent's own code. The custom retrieval quality checker was producing scores. The custom circuit breaker was catching failures. A custom telemetry layer was emitting structured events. All three had passed code review. When the OSS replacements arrived, the richer signals they emitted found two problems code review had missed: scores that were not comparable across runs, and circuit state transitions missing from telemetry. The agent replaced all three with OSS equivalents.

Fourteen shared primitives later, the operational layer covers every phase of a run: run correlation, structured telemetry, a retrieval quality checker, a circuit breaker, budget guardrails, lineage manifests. OSS where it covers the problem (RAGAS, pybreaker, OpenTelemetry), custom code only where it doesn't. No cloud APIs are required; the data stays local. The coding agent reads the evidence bundle keyed by a single run ID, not the source inputs.

The 14 primitives

Together they bound what can go wrong when no one is watching: every run has a timeout, a budget, a degrade mode, and a unique run identifier. A shared package provides them as callable helpers.

  1. Run correlation: assigns each pipeline execution a unique run identifier and propagates it across all modules so every telemetry event, manifest, and artefact can be correlated end-to-end.
  2. Structured telemetry: emits JSON events (LLM call, tool call, eval result, feedback) to application logs and optionally to a JSONL file; content-safe by default, raw prompts never logged.
  3. Embedding observability: wraps embedding calls to emit telemetry and track per-run counters (calls, batches, texts, failures) in a thread-safe in-memory store separate from the event stream.
  4. Lineage manifests: writes structured, replayable records for every run and every corpus ingestion, keyed by the run identifier.
  5. Cost estimation: token estimation and pricing model; every model call emits estimated prompt tokens, output tokens, and cost so spend is visible without a cloud billing dashboard.
  6. Cost guardrails: optional per-run budgets enforced before each LLM call; budget breaches emit structured telemetry rather than raising unhandled exceptions.
  7. LlamaIndex + OpenTelemetry tracing + metrics: LlamaIndex callback instrumentation with optional OTLP span export; content-safe by default; canonical OTel meters (call duration, token totals, cache hits, budget breaches, cost) exportable via OTLP.
  8. Contract helpers: stable error and result envelopes at module boundaries so failures are structured rather than surfacing as raw exceptions.
  9. Evaluation harness: two modes: expected-based (CI, repeatable, zero LLM calls) and RAGAS-scored (faithfulness, answer relevance, context precision); retrieval metrics (Hit@k, MRR, NDCG).
  10. Feedback events (HITL): standard feedback format tied to the run identifier; full improvement loop from captured feedback events through privacy-safe dataset export to prompt or config adjustment and re-evaluated baseline.
  11. Semantic cache + guardrails + artefact registry: two cache levels (LLM-call and retrieval/query) using embedding similarity; YAML guardrail rules for PII and injection tripwires; artefact snapshot, promotion, and rollback pointers.
  12. Ops reporting + retention: per-run review (verdict, warnings, key metrics, pointers to telemetry and manifests), run comparison delta, verdict history index, and age/size-based retention cleanup.
  13. Artefact promotion / rollback: CLI for promoting corpus, graph, and index snapshots to named pointers; rollback is a re-promotion.
  14. Circuit breaker: wraps provider calls with an open/half-open/closed state machine; trips before a stalling local model burns the run budget; circuit state transitions appear in the telemetry stream alongside call latency and degrade modes.

What the agent reads

These primitives emit two tiers of signal the agent reads to diagnose failures: LLMOps signals available immediately after a run, and RAGOps signals that require a retrieval quality assessment first.

The LLMOps signals appear immediately. Readable as soon as a run completes:

  • Circuit breaker state: catches provider stalls before the run burns its budget on dead calls.
  • Output completion reasons: high truncation rates mean outputs are being cut short; high context overflow rates mean the context window is undersized for the workload.
  • Token budget consumption rate: if the model is spending its budget before producing output, the signal appears here before results start failing.

RAGOps signals require a retrieval quality assessment first and cover a different class of failure:

  • Retrieval metrics (Hit@k, RAGAS faithfulness, context precision): catch quality regression that produces no error: the model answers, but not from the right chunks.
  • Reconciliation checks: catch ingestion fragmentation: when sparse and dense index counts diverge, the ingest is structurally broken.
  • Cross-run comparison: makes regression visible; a change that fixed one signal while degrading another only shows up here.

Both tiers are addressed from a single run identifier, without touching source data, model outputs, or prompts.

How a coding agent reviews a run

Each pipeline execution is assigned a unique run identifier. After any workload executes, everything that happened is searchable from that single identifier: telemetry events, run manifest (a structured record of what the run produced: status, config fingerprints, model identifier, error counts), ingestion manifest (the equivalent for the ingest pipeline: chunker settings, parser, document counts), run review verdict, and a comparison against the previous run. The agent does not need to re-run anything, inspect any data, or read any model output to diagnose what went wrong.

The verdict can be pass, ok_with_warnings, fail, or degraded; each points at a different intervention class. In practice, a run that completes with ok_with_warnings might name context_overflow as the flagged signal type. This directs the agent to open telemetry, scan for context_overflow events, and locate them within a single pipeline stage. That points to the context budget for that stage, not the model or the data. One config change, one re-run. run_comparison.json confirms the signal cleared without degrading anything else.

The loop is: read the evidence trail, form a diagnosis from specific field values, apply one targeted intervention, re-run, verify.

The signal determines the intervention type. A config parameter out of range is a quick fix; one change, one re-run. A structural problem in the implementation is not: the code changes, and if it touches how data was processed upstream, the corpus has to be rebuilt and re-ingested. A comparison against the previous run shows whether the targeted signal moved.

Each failure made visible

When local Ollama model calls started stalling under load, the circuit breaker tripped before the run burned its budget on failed calls. The run stopped cleanly. The cause was already in telemetry. There was a run record to read, not a crash to recover from.

Retrieval quality was a harder problem because nothing broke. The run completed, the model answered, but the answers were coming from the wrong chunks. The retrieval quality checker made it visible: scores had dropped on this specific run, and run correlation showed exactly when it happened.

The diagnosis led back to ingestion. The source was a multi-page definitions table from a corporate policy handbook: rows that only made sense as complete units. The chunker was splitting them mid-row, producing short incoherent fragments that ranked weakly in both indexes.

That pointed at the PDF parser and the chunking strategy simultaneously. The agent tested three parsers against the same document: the first lost table structure entirely, the second fragmented it, the third retained it intact. The retrieval signals showed the pattern at each step. The metrics confirmed the selection.

Each failure had been caught by a different primitive. Each primitive has a defined role. Run correlation makes before/after comparison possible. The retrieval quality checker finds quality problems that produce no error: when relevant chunks aren't returned, the only signal is degraded answers. Reconciliation catches fragmentation precisely because index count mismatches raise no exception; ingestion metrics identify the cause. The circuit breaker keeps a stalling local model from taking the whole run down.

The agent recognised it had rebuilt OSS

The signals that exposed pipeline failures eventually found problems with the custom implementations themselves. The governance contract said to prefer OSS over custom code; the agent had ignored that preference during the initial build.

A rule without a named consequence gives an agent nothing to weigh. When the governance rules were rewritten to name the specific failure each prevents, and sessions were anchored to a document of what had been built, a fresh session read that record and evaluated the custom implementations against rules it could now actually see. The gaps were there: scores not comparable across runs, incomplete circuit breaker telemetry, non-portable spans. The rule, the evidence, and the gap were all visible at the same time. A subsequent session replaced all three with RAGAS, pybreaker, and OpenTelemetry.

RAGAS: evaluation

RAGAS scores against an industry benchmark. Faithfulness, AnswerRelevancy, and ContextPrecisionWithoutReference mean the same thing here as on any other system that uses them. The judge runs against a locally-hosted Ollama model at £0 in API calls.

https://gist.github.com/paterake/9cb435847041d2c6279f358741f351dc

RAGAS judge scoring: faithfulness, answer relevancy, and context precision evaluated against a locally-hosted Ollama model.

pybreaker: circuit breaker

When a local model stalls, pybreaker trips the circuit before the run burns its budget on dead calls. Open, half-open, and closed state transitions are structured telemetry events. The cause lands in the run record, not in logs.

OpenTelemetry: tracing and telemetry

Every LLM call and tool call emits spans using GenAI semantic conventions. Model identifier, token counts, and operational state carry standardised attribute names. Any OTLP-compatible backend can read them without custom parsing.

The full stack

The migration (RAGAS, pybreaker, OpenTelemetry) replaced custom implementations within the operational layer. The broader foundation underneath:

  • Ollama: local model serving and embeddings, no cloud required
  • LlamaIndex: retrieval framework; index construction, querying, and callbacks
  • ChromaDB: vector store for dense retrieval
  • llama-index-retrievers-bm25: sparse retrieval keyword index
  • RAGAS: evaluation metrics; faithfulness, relevancy, and context precision
  • pybreaker: circuit breaker; open/half-open/closed state management
  • OpenTelemetry: tracing and metrics via OTLP spans and GenAI semantic conventions
  • Redis (optional): semantic cache backend

The OSS signals improved solutions that were already built

The RAGAS, pybreaker, and OpenTelemetry replacements improved signal coverage, not code quality. The agent had tuned the custom implementations to detect the specific failures it was diagnosing at the time. The OSS solutions caught problems the custom implementations were never built to see. Two modules I had called done were not.

The classifier was the first of those two modules. Per-call counters showed the LLM was being called on nearly every query. Every LLM call has a cost; cheaper methods that could have answered the same query were going unused. The output looked correct; only the call volume showed the problem. The richer telemetry made a different design visible: put the LLM at the end of the chain, behind exact match, fuzzy match, and embedding similarity, called only when the cheaper layers cannot answer. Only genuinely new queries reach the model.

The visualisation pipeline was the second. Budget tracking showed the model burning its generation budget before producing any chart output. The cause was chain-of-thought: with thinking mode enabled, the model was spending its token budget reasoning about what charts to draw, then timing out before drawing any. The fix was a single config change: disabling chain-of-thought for that run type, applied to the shared config rather than the module. The module never needed changing. The signal told the agent exactly where to look.

Both of those fixes happened after the agent had reviewed the solutions and considered them complete. The operational layer found gaps that code review had not found, because neither code review nor the agents could see call volume or budget consumption from the output alone.

The CI gate: repeatable evaluation, zero LLM calls

The telemetry is for operational diagnosis after a run. The eval harness serves a different purpose: it gives the coding agent a quality verdict on every code change, before anything ships, without running against real documents and without any cloud cost.

When the agent makes a change, it can run the eval tests locally and know immediately whether answer quality has held. In the automated build pipeline, the same tests run on every commit: if answers have regressed against the known-good set, the build fails.

This is only possible because the pipeline tests use pre-written expected answers rather than an LLM judge. The harness enforces this in code. Requesting scoring metrics without a pre-written answer raises an error before any model call is attempted.

What I learned

The operational layer existed before I knew what to call it. The first version was a circuit breaker event and a retry counter. The fourteenth primitive came much later. I planned none of them. Each one solved something the signals eventually made visible.

Two modules I thought were done had structural problems I could only see once the OSS signals were in place. The classifier's call volume was wrong. The visualisation pipeline's budget allocation was wrong. Both had passed code review. Neither was visible from the output alone.

The agent-initiated refactor was the moment the system started working as intended. The agent could evaluate its own implementation against the signals it was emitting, find the OSS solution that covered the same ground more completely, and apply the replacement. That is what I had wanted from the beginning, more or less. The signals made that possible.

Not one of those fixes waited for a human to notice.

When the pipeline processes ten years of historical enterprise data in a single run, there is no practical path for a human to verify the outputs. The LLMOps and RAGOps signals are the verification: budget guardrails cap runaway spend, circuit breakers catch provider stalls, eval gates confirm retrieval quality has not regressed, and the run review verdict names what to inspect if anything has. The agent reads the evidence bundle and acts on what the signal values show.

I set the constraints. Everything else is the agent.

Key takeaways

  • Fourteen primitives give a coding agent a complete evidence layer to diagnose failures from a single run ID, without touching source data, model outputs, or prompts.
