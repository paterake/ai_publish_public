How Shared Governance Stops AI Agents Forgetting

Image created by the author using Midjourney

Why one governance layer, synced as a dependency into every repo, is the one approach that prevents AI Coding Agents from drift.

I have been coding since before I had a computer of my own. Back then, walking past a Dixons or Tandy was reason enough to go in. I'd find the demo units and start coding, nothing ambitious, just enough to leave a humorous message on screen or tie the keyboard up in a way the next customer wouldn't expect.

I have since coded in Basic, Assembly, CICS COBOL, Pascal, Java, Scala, Python, and SQL across nearly four decades. The languages changed. The itch never did.

Coding was always the tool I used to translate a complex problem into something real and working. I'd take a business requirement apart and watch it resolve into something that runs. That satisfaction hasn't gone anywhere. Watching a framework outgrow its original problem and start solving ones I hadn't designed it for is better still.

Most vibe coding articles are written by people who are excited they can build things they couldn't before. That's not my story. Vibe coding didn't kill my desire to code. It closed the gap between a requirement and a working solution.

What did change was my relationship with the code itself, specifically how I know it's right.

I'm a hi-fi audiophile. I know what a well-matched CD player, amp, speakers, and cables can produce: a holographic soundstage, instruments placed in space, the sense that music is happening in the room rather than projecting from two boxes on a shelf. I know what that sounds like when it's right.

I have no desire to open the amplifier to validate how it produces that result.

The controls I've built around my agents work the same way. I no longer read the code the agent produces. At most a cursory glance at the overall structure. The controls generate the evidence. The evidence tells me whether what came out matches what I expect good code to look like: modular, driven by configuration, no domain context in the implementation, lineage and auditing in place. When the evidence passes, I trust the output. The soundstage is there.

My role didn't disappear. It shifted. I used to be the person who wrote the code. Now I'm the person who sets the standard, and the agent produces to it. The craft is still there. It just happens earlier in the process.

Building controls I could actually trust is what most of the work turned out to be.

Without them, you trust agent output by reading it. With them, you trust it through evidence. That scales. Personal code review doesn't.

The gap between fast and good

The early wins were obvious. What I didn't notice was what I was deferring.

As I shipped solutions, I kept having the same conversation with the agent. Every new session, every tool switch, I was re-establishing the same baseline. The same things, every time: keep solutions modular, drive everything through configuration rather than hardcoding assumptions into the code, build on existing libraries rather than from scratch, and make sure everything leaves a proper audit trail.

These aren't preferences. They are the defaults of someone who has watched what happens to systems that don't start from these principles. Systems that look clever in year one become expensive in year three.

I moved the requirements into the PRDs. That worked until the PRDs got heavy, intent and controls tangled together, neither readable on its own. I moved the controls out into project-level configuration. That worked until I had multiple projects, copied the controls across each, enhanced them separately, and watched them drift. One project had tighter security posture. Another had better operational bounds. Neither had the best of both.

I stopped. I was solving the same governance problem in every project, slightly differently, slowly building up a multi-headed control layer with no single authoritative source.

As a data engineer, you are trained to recognise this pattern and centralise the canonical version. Every consumer inherits from it. Projects add only what is genuinely unique to them, without touching the platform-level controls.

That is what I built. A governance layer that loads before any assistant starts work, holds across sessions, and ships into every governed repo as a dependency rather than a copy. I came to call it the PCO (Policy, Control plane, Observability).

Rolling out Claude Code to the masses (or any coding agent)

What caught me out across my own projects gets a lot worse at enterprise scale.

Roll out vibe coding to twenty engineers without shared governance and each one defines good in their own way. Output from one agent looks different from another's. Code from one team can't couple cleanly to code from a second. You won't know this for months, by which point the integration work costs more than the original builds did.

You end up reworking solutions whose inconsistency was invisible at delivery. Not because the engineers were careless. Because nobody established a shared definition of what the agent should produce before it started producing.

And it doesn't matter which tool they're using. Claude Code, Trae, Cursor, Copilot. Each one starts cold in every session with no knowledge of decisions made before or by anyone else on the team. The tool is not the problem. The absence of shared governance is.

One governance layer, inherited by every project, running before the first prompt lands.

The same structure applies whether you are a solo developer managing three repos or a team scaling across fifty.

How governance loads

In my setup, three assistants (Claude Code, Trae, and Qwen Code) all enter each repo the same way. Governance arrives in two layers.

The first is automatic. In these three assistants, rule files covering security posture, operational bounds, agent behaviour, and context economy are injected by the harness before the session processes any message. The assistant didn't choose to read them. They were pushed.

The second is instruction-following. The entry point (one line) directs the assistant to a routing file. That file defines a mandatory read order: platform rules first, project-specific context second — blocking pillars, task routing, and the project's active backlog.

The entry point routes into ai_context/, which splits into two layers: pco/, the synced read-only platform layer, and project/, the repo-owned additive layer. Each has its own ASSISTANTS.md — the platform one loaded first, the repo one second.

Inside the platform layer, each directory has a distinct job:

  • governance/: the shareable contract, registries, and ten domain folders — one per spoke — defining controls and evidence expectations
  • ai_harness/: enforcement surfaces that make the contract real in practice
  • rules/: policy packs (blocking and advisory) expressed in an enforceable format
  • hooks/: interceptors that stop unsafe actions before they execute
  • skills/: versioned procedures for repeatable task classes — data analysis, context sync, code review, documentation generation

Rules constrain what the assistant may do; skills define how a repeatable task must be executed.

This is what separates a governed repo from an ungoverned one: the controls don't wait to be explained. They arrive before the assistant has a choice.

Getting to that point meant treating governance as a data engineering problem, not a prompting one.

The cost of consistency

One problem. Ensuring that the rules governing how an assistant works persist across sessions, across tool switches, and across repos, without re-setup and without drift.

The governance layer has a measurable, bounded cost. The full layer, 11 rule files plus routing and entry-point files, totals roughly 40KB of text — approximately 10,000 tokens, or about 5% of a modern 200K context window. It loads once and holds across every turn in the session. The design target is 5–10% of context, enough to anchor behaviour, small enough not to crowd out the actual work.

Without governance, a session re-derives constraints from conversation history as it grows. Earlier rules lose weight as task signals accumulate, the cost is invisible, paid on every turn, and compounds with session length. That 5% is the price of consistency. The alternative is drift that looks like progress until it isn't.

Context saturation compounds when work spans multiple sessions. The PCO contract covers this: long-running work is designed in sessions rather than accumulated in one — each session starts from an anchor document that records current state, next step, accumulated constraints, and known gotchas. The session starts warm from recorded state, not by re-reading old transcripts. Work hands off cleanly between sessions, or between agents, without losing what was established.

Token costs grow with ungoverned sessions. Without a governed context layer, each session re-establishes the same constraints from scratch. Utility code gets re-implemented because its existence only lived in a previous chat transcript.

Agent loops have no natural stopping point. An agent executing a multi-step plan without execution limits, verification gates, or evidence checkpoints can drift far from intent before any failure surface triggers. The failure mode is not an error. It is a confident wrong answer that passed all the local checks and got committed.

What I learned building it

What cost me most looked like "everything is fine":

Governance exceptions are easy to justify once and easy to forget. The first one was warranted, unblock a specific delivery while the platform was still evolving. By the next review, nobody was treating it as an exception any more — it had become the default. Exceptions need a fixed end date; when they lapse, the original constraint must reassert, not quietly persist.

An agent will tell you the task is verified. The only evidence is a sentence in a chat transcript from a session that's gone. The fix is a check you can re-run independently, not "do I believe the agent?" but "can I run this myself and see the same outcome?"

Drift doesn't show up until you have multiple repos. A local patch to a governance control feels harmless in one place. Across several projects, each patched slightly differently, the controls have quietly diverged — and the inconsistency only surfaces when the projects need to work together.

Evidence is not durable by default. During a restructure I lost the records of what previous agent runs had produced — sitting in an ignored folder, gone after a tidy-up. Nothing broke in the code. What broke was my ability to prove what had worked before. Those records are a first-class output, not a convenience file.

What PCO is

  • Policy — The responsibility: Decide what's allowed, under what constraints — What makes it real: Blocking constraints and explicit decision rights
  • Control plane — The responsibility: Route work through approved workflows — What makes it real: Consistent routing, tools with limited scope, explicit stop and deny points
  • Observability — The responsibility: Prove what happened and detect drift — What makes it real: Run evidence, lineage, audits, exception/approval records

If you only have policy text, you don't have governance. You have preferences.

Three requirements apply to every run regardless of risk tier:

  • Signal uncertainty rather than producing a confident wrong answer
  • Never represent the assistant as human in any channel
  • State assumptions before acting; when multiple interpretations exist, present them rather than picking one silently

Filling gaps without flagging them is how agents deliver exactly what was asked for in a way that wasn't intended. A platform that allows any of these to be overridden through conversation is non-conformant.

The governance model: hub-and-spoke

The platform is structured as a hub-and-spoke, borrowed directly from how data engineering governs shared master data across many pipelines and consumers. One authoritative source, consumed as a dependency.

The hub owns the canonical standards: decision rights, how policies are classified and enforced, risk tiers, approvals, and evidence requirements. Downstream repos consume it. They do not fork it.

I kept coming back to this structure because I had seen the alternative: local fixes that worked until the next sync overwrote them silently, platform improvements that never propagated.

The spokes are the governed domains. Each spoke defines controls and evidence expectations for one area of the platform without constraining internal implementation. Four spokes are where the pain shows up first:

  • Behaviour & Design — Behaviour as a fixed contract: role, permitted tools, and how uncertainty is handled. Loaded at session start; cannot be overridden through conversation
  • Runtime & Operations — How a run is managed: bounded retries, clear stopping conditions, cancellation support, and a requirement that every run is reproducible from its recorded inputs
  • Security & Safety — Controls that stop data leaking out: credentials scoped to the task, and a hard rule that sensitive data, untrusted content, and external write access must never coexist in the same session
  • Assurance & Evals — Evaluation as a blocking gate at three levels — final answer quality, sequence of actions taken, and multi-turn consistency — with versioned datasets and a loop that converts production failures into regression tests

Six further spokes govern agent architecture patterns, tool registries, knowledge retrieval, identity and entitlements, telemetry and cost attribution, and versioning and lineage.

Spokes can evolve independently; they remain accountable to the hub's non-negotiables. A project adds a repo-owned layer on top, additive context that must not contradict the platform.

Risk tiers and enforcement

The platform uses explicit risk tiers so enforcement is calibrated to actual risk rather than applied uniformly:

  • Low — Typical work: Small changes, formatting, non-sensitive refactors — Enforcement: Minimal approvals; standard evidence
  • Medium — Typical work: Feature work, moderate refactors — Enforcement: Stronger verification; limited tool entitlements
  • High — Typical work: Security-sensitive, broad refactors, release tooling — Enforcement: Human-in-the-loop approvals; restricted tools
  • Critical — Typical work: Production impact, secrets/identity, destructive operations — Enforcement: Fully supervised workflow; independent review

Rule files are guidance. They inform behaviour but lose weight as a session grows long. Hooks are enforcement. They execute at defined points regardless of session length, model output, or instruction drift. The model has no prose path around them. At most it can choose different actions that avoid the gated operation.

In my implementation, one hook defers git push to main for human approval and returns a structured denial that includes risk tier, policy set, and the next action.

When a rule is violated, the shape of that response is fixed, auditable rather than conversational:

Action denied by governance policy.
Reason: Protected change requires approval at this risk tier.
Next: request approval or scope down the change.

A reviewer can always explain why an action was blocked. That is the difference between a denial that proves governance and a denial that just stops work.

If nothing ever fails, the "policy" is only persuasion. Persuasion does not survive long sessions.

The proof without link spam

This article is the proof, it shows what the system looks like from the outside, without requiring access to the implementation behind it.

Three things make the claim verifiable. The contract shows there is a stable "what must be true" layer, independent of tooling. The operating model shows governance exists as a lifecycle, not a policy PDF, it defines the evidence outcomes a run must produce. The routing rules show that assistants enter each repo through governance deterministically, not via "whatever was in the chat".

The contract alone shows intent. The operating model shows it works consistently, the same evidence every run. The routing rules show it holds when you switch tools or start a fresh session.

How it ships without drift

The platform has to exist where the work happens: in downstream repos. But copy the files into every repo and you get the slowest failure mode in engineering, divergence that looks fine until it matters.

The distribution model: a synced platform folder (read-only for consumers), a repo-owned additive layer, and a deterministic router at the repo root. Downstream repos consume the platform as a dependency. They do not fork it.

When a repo discovers a platform gap, it doesn't fix it locally. It produces a structured gap report and pushes the fix upstream, so the next sync corrects every repo at once. Local hotfixes are how the platform silently forks.

The platform can audit itself: detecting contradictions between declared policy and required artefacts, missing mandatory registries, and expired exceptions still treated as active.

The overhead makes sense when you have multiple repos and more than one assistant. A single-repo, single-tool setup carries much of the overhead without much return. The investment pays back when you hit the first tool switch that requires no reset, or when a platform fix propagates to three repos at once instead of being applied to each separately.

Key takeaways

  • One governance layer, synced into every repo as a dependency rather than a copy, is the only structure that doesn't drift as tools and projects multiply.
  • Policy text informs behaviour. Hooks enforce it. The difference is whether a rule can be ignored without anything failing.
  • Downstream repos consume governance as a dependency. They do not fork it.

If you want to adopt the pattern

  • Define non-negotiable pillars that apply to every run
  • Define risk tiers and supervision levels (and bind them to verification and entitlements, because tiers without entitlement differences are decoration)
  • Bound tool access by role and risk tier, and make it traceable
  • Require minimum evidence per run (run_id, policy binding, tool/model identities, verification outcomes)
  • Write exceptions down, give them an end date, and name who owns them (grant the same exception twice without reviewing it and the exception has become the rule)
  • Put change control in force for policy, tools, and workflow updates
  • Ship the platform as a dependency into governed repos (no forking; no local overrides, because a local override is how drift starts)
  • Put a deterministic router in every repo so context is conditional, auditable, and budgeted

If you can't prove conformance with evidence, you don't have governance.
